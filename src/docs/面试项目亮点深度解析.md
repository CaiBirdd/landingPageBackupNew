## 🌟 亮点一：PC / Mobile 双端组件独立渲染方案

### 🔴 面试切入点
“在落地页开发中，为了追求极致的首屏体验和代码可维护性，我没有采用常规的 Media Query 响应式适配，而是设计了一套**基于 User-Agent 的组件级分流架构**。”

### 1. 业务场景与挑战
传统的 CSS 媒体查询方案存在以下痛点：
1.  **代码冗余**：一套 HTML 的情况下往往要写两套差别巨大的 CSS。
2.  **交互与布局差异大**：PC 端是复杂的相对与绝对定位结构，Mobile 端是单列流式布局。勉强共用 DOM 会导致维护灾难。
3.  **性能损耗**：移动端加载了大量 PC 端才需要的样式。

### 2. 核心技术实现：User-Agent 组件分流
在 `App.vue` 入口处，直接根据设备类型动态阻断并分发渲染。

**代码复现 (App.vue)**：
```javascript
<template>
  <div>
    <!-- v-if 确保组件完全隔离，DOM 树中只会存在其中一个，极致精简首屏 DOM -->
    <LandingPage v-if="!isMobile" />
    <LandingPageMobile v-else />
  </div>
</template>

<script setup>
import { ref } from 'vue'
// 此处异步组件引入 (如 defineAsyncComponent) 可以进一步优化性能（面试加分项）
import LandingPage from './views/landingPage.vue'
import LandingPageMobile from './views/landingPageMobile.vue'

// 检测设备类型
const detectDevice = () => {
  const userAgent = navigator.userAgent.toLowerCase()
  // 更严谨的正则匹配主流移动端设备
  return /mobile|android|iphone|ipad|phone|blackberry|iemobile|wpdesktop/i.test(userAgent)
}
const isMobile = ref(detectDevice())
</script>
```

### 3. 首屏性能跃升：移动端 VW 视口适配
为了在移动端实现对设计稿的“像素级”还原（Design Width: 440px），我们抛弃了包含运行时 JS 计算的传统 REM 方案，采取了目前前端界最推崇的 **PostCSS-px-to-viewport** 方案。

**Why VW over REM?**
早期的 REM 适配需要在客户端执行一段 JS 来计算当前视口宽度并动态给 HTML 赋值，同时还要监听 `resize` 极易造成性能抖动。而基于 `vw` 的方案将转换链路前置到了**构建流程 (Build Time)** 中处理。代码中按设计稿写死 px，通过 Vite 与 PostCSS 插件，打包时直接根据比例算出各个元素的 vw 值并落盘成静态 CSS。这极大地减轻了终端浏览器的运行时计算压力，彻底抛弃了对阻塞渲染的内联 JS 脚本的依赖，也规避了潜在的内存泄漏风险。

**配置细节 (vite.config.js)**：
```javascript
import pxtoviewport from 'postcss-px-to-viewport-8-plugin';

export default defineConfig({
  css: {
    postcss: {
      plugins: [
        pxtoviewport({
          viewportWidth: 440, // 视口宽度，精准对应设计稿基准宽度
          unitPrecision: 5,
          viewportUnit: 'vw', 
          propList: ['*'],
          selectorBlackList: [
            'ignore-',
            'header-section-pc', // 关键！过滤掉PC专属组件，防止影响
            'landing-content-pc'
          ],
          replace: true,
          mediaQuery: false,
          minPixelValue: 1 
        }),
      ],
    }
  }
})
```

## 🌟 亮点二：营销数据闭环 (流量来源 -> 用户行为 -> 转化归因)

### 🔴 面试切入点
“为了解决广告投放中‘流量归因断层’的痛点，我封装了一套 UTM 参数解析模块，打通了 Session ID 与 PostHog/Pixel 的数据链路，实现了从**广告点击**到**用户转化**的全链路追踪与画像构建。”

### 1. 业务逻辑闭环
打破“全栈只做页面”的刻板印象，展示业务思维：
- **上游链路**：解析 Facebook/Google 广告的 UTM 参数。
- **中游链路**：以 Session ID 串联用户行为，使用 LocalStorage 持久化，防止刷新丢失追踪。
- **下游链路**：数据分发到自建后端（引流记录）、PostHog（行为漏斗）与 Facebook Pixel（算法模型优化）。

### 2. 核心代码：URL 取参引擎与 Session 换取
在首屏加载时捕获所有 URL 参数，与后端换取长期交互依赖的 `session_id`。

**代码复现 (FeedbackForm.vue 等核心组件)**：
```javascript
const getUrlParams = () => {
  const params = new URLSearchParams(window.location.search)
  const utmParams = { device: getDeviceType() } // 默认携带设备指纹

  // 提取各维度的广告属性，扁平处理
  const campaign_name = params.get('campaign_name')
  const adset_name = params.get('adset_name')
  const ad_name = params.get('ad_name')
  const ad_content = params.get('ad_content')
  // ... 其他属性提取
  
  // 按需挂载，避免脏数据传入后端
  if (campaign_name) utmParams.campaign_name = campaign_name;
  if (adset_name) utmParams.adset_name = adset_name;
  if (ad_content) utmParams.ad_content = ad_content;
  // ...

  return utmParams
}

const recordUtmParams = async () => {
  const utmParams = getUrlParams()
  const hasUtmParams = Object.keys(utmParams).length > 1
  
  // 优化：仅在有实际广告参数时才发起请求，不白耗后端资源
  if (!hasUtmParams) return
  
  const res = await recordUtmParamsAPI(utmParams)
  if (res.data?.session_id) {
    // 关键：持久化到 localStorage
    // 解决用户刷新页面，或中途跳出再返回导致的归因断层问题
    localStorage.setItem('session_id', res.data.session_id)
    formData.value.session_id = res.data.session_id
  }
}
```

### 3. 三端同步埋点与上报 (自建库 + PostHog + FB Pixel)
真正的转化发生时，执行精准的三端切面拦截：

```javascript
/* FeedbackForm.vue 内的 sendData 方法逻辑 */
const sendData = async (data, submitType) => {
  // 1. 业务落库：提交数据到自家服务端
  const res = await createFeedbackAPI(data)

  if (res.status === 201) {
    // 2. 产品行为分析 (PostHog)：全方位捕获内容细节与属性标签
    posthog.capture('feedback_submitted', {
      email: data.email || '',
      feedback_content: data.content || '',
      session_id: data.session_id,
      submit_type: submitType,
      has_feedback: !!data.content,     // 布尔转换提取核心状态信息，用于漏斗
      has_email: !!data.email,
      feedback_length: data.content ? data.content.length : 0 
    })

    // 【高光】Identify 用户唯一身份：结合业务把无名游客转化为具名用户
    if (data.email) {
      posthog.identify(data.email, {
        email: data.email,
        last_feedback_time: new Date().toISOString()
      })
    }

    // 3. 广告价值预估及回传 (FB Pixel)
    trackLead({
      content_name: submitType === 'email' ? 'Email Submission' : 'Feedback Submission',
      content_category: 'Lead',
      value: 1.00,       // 设定转化生命周期价值
      currency: 'USD'
    })
  }
}
```

## 🌟 亮点三：运营决策看板 (多级漏斗清洗与 A/B 测试追踪)

### 🔴 面试切入点
“为了量化投放素材质量，并对比分析‘功能导向 (Function)’与‘痛点导向 (Painpoint)’等广告表现，我开发了后台运营体系。利用 Vue 3 的 Computed 特性实现**前端响应式漏斗分层计算与实时 CVR 推导**，大幅减轻了后端的数据聚合压力。”

### 1. 技术落地：前端响应式数据漏斗与实时 CVR
不依赖后端报表聚合接口，在前端依托原始数据集 `allData` 自动清洗多级转化梯度（无效流量、部分转化、核心转化）。

**代码复现 (FeedbackDataManagement.vue)**：
```javascript
// 总数据量
const total = computed(() => pagination.value.total)

// 利用 computed 缓存优势处理漏斗分级
const hasEmailOrFeedback = computed(() => {
  return allData.value.filter((item) => item.email !== '未提交' || item.feedback !== '未提交').length
})

// 无效广告点击层
const utmOnly = computed(() => {
  return allData.value.filter((item) => item.email === '未提交' && item.feedback === '未提交').length
})

// 核心资产层：产生高频次意愿
const emailAndFeedback = computed(() => {
  return allData.value.filter((item) => item.email !== '未提交' && item.feedback !== '未提交').length
})

// 实时转化率计算
// CVR = (有邮箱或反馈的条数 / 直推总条数) * 100%
const cvr = computed(() => {
  return total.value > 0 
    ? ((hasEmailOrFeedback.value / total.value) * 100).toFixed(2) 
    : '0.0'
})
```

## 💡 深度面试问答 (Q&A 预案)

### Q1: 你的 CVR (转化率) 与漏斗为什么要在前端通过 `computed` 算？而不是写个 SQL 让后端聚合返回？
**答：** 
由于项目处于**早期快速试错与验证阶段 (MVP)**，业务需要极其灵活的多维度交叉对比看板：
1. **敏捷响应迭代**：如果明天运营想看“仅提交反馈而没留邮箱”的特定层级，纯前端可以在 3 分钟内新增一个 `computed`；如果在后端实现则可能需要修改 SQL 聚合逻辑、写新接口。
2. **性能与体验双赢**：利用 `allData` 存储下发的列表无分页全明细数据，通过 Vue 3 `computed` 的依赖收集和缓存机制，数组过滤 `filter` 耗时几乎微乎其微。
3. **架构演进约束**：当然，这是在数据量不爆炸（例如不卡死网络传输和浏览器内存）时的策略。如果后续数据量级突破大关，必然要将清洗计算流转回后端的数仓服务做离线或者实时预处理，前端回归纯正的展现层。

### Q2: 移动端适配为什么选用 `vw` 而不是 `rem`？它的优势在哪里？
**答：** 
我在初版方案中用过 `rem`，但最终重构为了行业主流的 `vw` 方案，原因如下：
1. **解耦 JavaScript 和渲染阻塞**：`rem` 需要在 `<head>` 中插入一段内联脚本实时计算并动态修改根字号，甚至需要挂载和卸载 `resize` 监听。这从一定程度上污染了业务代码。而 `vw` 是纯 CSS层面的原生解法，它借助 PostCSS 构建工具，在打包环节就把适配比例确定了，直接输出纯净的 CSS。
2. **性能与兼容性优势**：现代浏览器对 `vw / vh` 视口单位的支持率早已非常成熟，性能也远远好于运行时的 JS DOM 改写。结合构建时的 `selectorBlackList` 黑名单过滤，更可以将那些不需要适配移动端的 PC 组件轻松摘除，实现了极高的工程化弹性。

### Q3: 从业务层面看，你的埋点策略解决了什么实际问题？
**答：** 
解决了最严重的**“投放盲打与效果断层”难题**。
1. 若只有前端表单和后端服务，我们只知道后台收到了五十封邮件，却根本不知道这是哪些广告（烧了多少钱）拿回来的线索。
2. 若只有 FB 侧，我们只知道有一百次跳转，却不知道转化的人具体的浏览设备、停留意愿和邮件信息是什么。
我通过在首屏生命阶段强制阻断并提取 URL 带过来的 UTM，主动调用 API 获取并 LocalStorage 持久化挂载唯一 `Session_id`，最终使得这三部分隔阂的数据：**“前端具体表现行为特征”**、**“外部推广系统特征”** 以及**“系统真实入账线索源”**融成了完整的长链闭环。从而反推指导下一轮投放到底是发“主打会议痛苦”的图片，还是“主打功能省时”的介绍信。


### Q4: 用户刷新页面，Vuex/Pinia 数据丢了，各种参数怎么保持？
**答：** 这也是我在项目中特意处理的点。

Session ID 持久化：UTM 参数换取的 Session ID 是存放在 localStorage 中的，它与 Vue 组件生命周期解耦。
生命周期恢复：onMounted 时，我会先查 Storage，如果有 ID，直接恢复到 formData 中。这保证了用户即使跳出页面去查个邮件回来（只要没关浏览器清理缓存），我们的归因链条依然是连通的。

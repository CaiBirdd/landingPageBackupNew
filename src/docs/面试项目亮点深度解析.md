    1.  **营销落地页 (Landing Page)**：投放于 Facebook/Google 广告渠道，用于展示产品核心价值（痛点/功能），收集潜在客户线索（邮箱/反馈）。

## 🌟 亮点一：PC / Mobile 双端组件独立渲染方案

### 🔴 面试切入点
“在落地页开发中，为了追求极致的首屏体验和代码可维护性，我没有采用常规的 Media Query 响应式适配，而是设计了一套**基于 User-Agent 的组件级分流架构**。”

### 1. 业务场景与挑战
传统的 CSS 媒体查询方案存在以下痛点：
1.  **代码冗余**：一套 HTML 要写两套 CSS，大量的 `display: none` 导致 CSS 文件体积膨胀。
2.  **交互差异大**：PC 端是左右分栏（左文右表单），Mobile 端是单列流式布局。DOM 结构差异巨大，强行共用 DOM 会导致维护灾难。
3.  **性能损耗**：移动端加载了大量 PC 端才需要的样式和脚本。

### 2. 核心技术实现：User-Agent 组件分流
在 `App.vue` 入口处，直接阻断不需要的组件渲染。

**代码复现 (App.vue)**：
```javascript
<script setup>
import { ref } from 'vue'
// 此处采用异步组件引入可以进一步优化首屏体积（面试加分项）
import LandingPage from './views/landingPage.vue'
import LandingPageMobile from './views/landingPageMobile.vue'

const detectDevice = () => {
  const userAgent = navigator.userAgent.toLowerCase()
  // 正则匹配所有主流移动端设备
  return /mobile|android|iphone|ipad|phone/i.test(userAgent)
}

// 响应式状态：决定渲染哪一套组件
const isMobile = ref(detectDevice())
</script>

<template>
  <div>
    <!-- v-if 确保组件完全隔离，DOM 树中只会存在其中一个 -->
    <LandingPage v-if="!isMobile" />
    <LandingPageMobile v-else />
  </div>
</template>
```

### 3. 极致体验：移动端动态 REM 适配
为了在移动端实现“像素级”还原设计稿（Design Width: 440px），我们采取了 **PostCSS + Dynamic REM** 方案。

**Why not VW?**
虽然 VW 是现代主流，但在部分老旧安卓机型通过系统设置调整字体大小时，REM 方案的兼容性和可控性更好。通过 JS 动态计算，我们可以精确控制最大宽度（避免在 Pad 上过宽）。

**代码细节 (landingPageMobile.vue)**：
```javascript
const DESIGN_WIDTH = 440; // 设计稿宽度
const ROOT_VALUE = 44;    // 1rem = 44px

const setRem = () => {
  // 限制最大宽度，防止在平板/桌面端铺满导致布局拉伸
  const clientWidth = Math.min(document.documentElement.clientWidth, DESIGN_WIDTH);
  
  // 核心公式：当前rem = (当前宽 / 设计稿宽) * 基准rem
  // 例如：屏幕宽 220px -> font-size = 22px -> 1rem = 22px -> 元素缩小一半
  const fontSize = (clientWidth / DESIGN_WIDTH) * ROOT_VALUE;
  
  document.documentElement.style.fontSize = `${fontSize}px`;
}
```

## 🌟 亮点二：营销数据闭环 (流量来源 -> 用户行为 -> 转化归因)

### 🔴 面试切入点
“为了解决广告投放中‘流量归因断层’的痛点，我封装了一套 UTM 参数解析模块，并打通了 Session ID 与 PostHog/Pixel 的数据链路，实现了从**广告点击**到**用户转化**的全链路追踪。”

### 1. 业务逻辑闭环
大部分前端只管“切图”，但这个项目要求前端懂“数据”。你的价值在于串联了孤岛数据：
- **上游**：Facebook 广告 (UTM 参数)
- **中游**：用户在 Landing Page 的行为 (Session ID)
- **下游**：后端数据库 (转化记录)

### 2. 核心代码：recordUtmParams 模块
这是一个独立的业务模块，负责在用户**首次**进入页面时“捕获”所有的广告参数，并向后端换取一个唯一的“身份证”——`session_id`。

**代码复现 (recordUtmParams.js & FeedbackForm.vue)**：
```javascript
// A. 提取广告参数（健壮性处理）
const getUrlParams = () => {
  const params = new URLSearchParams(window.location.search);
  const utmParams = { device: getDeviceType() }; // 默认携带设备信息
  
  // 提取关键字段：广告系列、广告组、广告创意、落地页变体
  ['campaign_name', 'ad_name', 'landingpage_variant'].forEach(key => {
    if (params.get(key)) utmParams[key] = params.get(key);
  });
  
  return utmParams;
}

// B. 换取 Session ID 并持久化 (Token 式管理)
const recordUtmParams = async () => {
  const utmParams = getUrlParams();
  // 优化：仅在有实际广告参数时才发起请求，节省服务器资源
  if (Object.keys(utmParams).length <= 1) return;

  try {
    const res = await api.record(utmParams);
    if (res.data?.session_id) {
      // 关键步骤：持久化到 localStorage
      // 解决用户刷新页面、或跳转后返回导致归因丢失的问题
      localStorage.setItem('session_id', res.data.session_id);
    }
  } catch (e) {
    console.error('归因记录失败'); // 实际生产中这里也会上报错误日志
  }
}
```

### 3. 双平台埋点体系 (PostHog + Pixel)
在用户提交表单（产生价值）的那一刻，我们需要同时通知**产品分析平台**（PostHog）和**广告投放平台**（FB Pixel）。

```javascript
/* FeedbackForm.vue */
const sendData = async () => {
  // 1. 业务请求：提交数据到自家后端
  await api.createFeedback(formData);
  
  // 2. 产品埋点：记录用户行为细节（谁？什么设备？提交了什么？关联的SessionID是多少？）
  posthog.capture('feedback_submitted', {
    email: formData.email,
    session_id: formData.session_id,
    has_feedback: !!formData.content
  });

  // 3. 广告回传：告诉 Facebook "这个人值钱"，帮助 FB 算法优化投放模型
  trackLead({
    content_name: 'Email Submission',
    value: 1.00 // 赋予转化价值
  });
}
```

## 🌟 亮点三：运营决策看板 (实时 CVR 与 A/B 测试分析)

### 🔴 面试切入点
“为了量化评估‘人工投放 vs AI 投放’的效果，我搭建了一个运营决策看板。利用 Vue 的 Computed 属性实现了**纯前端的实时 CVR 计算**与**多维 A/B 测试筛选**，大大降低了后端开发成本，提升了运营分析效率。”

### 1. 技术难点：前端实时计算 CVR
通常报表统计在后端做，但在数据量级允许（<10万）的情况下，前端计算响应更快，交互更流畅。

**代码复现 (FeedbackDataManagement.vue)**：
```javascript
// 定义核心指标：转化率 (Conversion Rate)
// CVR = (留邮箱数 + 留反馈数) / 总访问数

// 1. 利用 computed 缓存特性，仅在 allData 变化时重新计算，性能无忧
const cvr = computed(() => {
  const total = pagination.value.total;
  // 过滤出有效线索
  const validLeads = allData.value.filter(
    item => item.email !== '未提交' || item.feedback !== '未提交'
  ).length;
  
  // 边界保护：分母为 0 处理
  return total > 0 ? ((validLeads / total) * 100).toFixed(2) : '0.0';
});
```

### 2. 线索分层清洗 (Data Cleaning)
原始数据是扁平的，运营需要看到的是“分层金字塔”。通过 `computed` 将数据清洗为三个层级：
1.  **无效流量 (UtmOnly)**：只点了广告，进来啥也没干。
2.  **一般线索 (EmailOnly)**：留了邮箱，有订阅意向。
3.  **高价值线索 (Email + Feedback)**：既留邮箱又提需求，是核心目标用户。

### 3. 多维 A/B 测试筛选 (Element Plus + 响应式过滤)
这是一个典型的**复杂表单查询**场景。我们支持“广告内容 (Function vs Painpoint)”和“投放模式 (AI vs Manual)”的交叉筛选。

```javascript
// 筛选模型响应式对象
const filters = ref({
  adCampaign: '', // 筛选：人工投放 还是 AI投放？
  adContent: '',  // 筛选：主打功能 还是 主打痛点？
  landingPageVariant: '' // 筛选：文案A 还是 文案B？
});

// 监听变更 -> 重置页码 -> 重新拉取
const handleFilterChange = () => {
  pagination.value.page = 1;
  loadData(); // 这会触发后端查询，返回新的 dataset，随即触发 cvr 重新计算
};
```

## 💡 深度面试问答 (Q&A)

### Q1: 你的 CVR 为什么在前端算？数据量大了怎么办？
**答：** 
目前项目处于**早期验证阶段**（MVP），数据量级在万级以内。
1.  **敏捷性**：前端算可以快速对应运营频繁变化的指标定义（比如今天想算 Email 转化，明天想算 Feedback 转化），无需后端频繁改接口。
2.  **性能**：Vue 的 `computed` 机制非常高效，万级数据的遍历计算耗时在毫秒级，用户感知不明显。
3.  **未来扩展**：如果数据量超过 10 万，我会将计算逻辑下沉到后端，或者引入离线数仓（Data Warehouse）进行预计算，前端只做展示。

### Q2: 移动端适配为什么不用 `viewport` 单位？
**答：** 
`viewport (vw/vh)` 是很好的方案，但在本项目中：
1.  **最大宽度限制**：我们需要在 PC 浏览器或 iPad 上限制移动端页面的最大宽度（440px），如果用 `vw`，页面会随着视口无限变大，布局会崩坏。使用 JS 动态计算 `rem`，我们可以轻松写出 `Math.min(clientWidth, 440)` 这样的逻辑来锁定最大宽。
2.  **兼容性兜底**：虽然现在兼容性好了，但为了防止某些魔改 WebView 对 `vw` 支持不佳，REM 方案更稳健。

### Q3: 用户刷新页面，Vuex/Pinia 数据丢了，各种参数怎么保持？
**答：**
这也是我在项目中特意处理的点。
1.  **Session ID 持久化**：UTM 参数换取的 Session ID 是存放在 `localStorage` 中的，它与 Vue 组件生命周期解耦。
2.  **生命周期恢复**：`onMounted` 时，我会先查 Storage，如果有 ID，直接恢复到 `formData` 中。这保证了用户即使跳出页面去查个邮件回来（只要没关浏览器清理缓存），我们的归因链条依然是连通的。

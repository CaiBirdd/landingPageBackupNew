## 🌟 亮点一：PC / Mobile 双端组件独立渲染与精细化适配

**👨‍💻 面试官提问：** “我看你的简历里写了针对营销落地页场景，设计 PC / Mobile 双端组件独立渲染方案，能具体讲讲当时的业务背景，以及具体是怎么实现的吗？”

**🗣️ 您的回答（参考话术）：**

“好的。当时我们开发这个出海营销落地页时，老板明确要求 PC 端和移动端必须有两套各自适应的 UI 体验，来最大化承载邮箱和反馈等转化入口。所以当时 UI 设计师直接给了我两套差异非常大的原型图。如果强行用传统的 CSS 媒体查询的方法去写在一套结构里，不仅很难精确还原两端的原生布局，还会导致一套 HTML 里掺杂大量冗余的 `display: none`。

**更致命的是性能问题：** 移动端用户会被迫下载大量 PC 端专属的 CSS 和交互脚本，首屏加载会非常吃亏。对于一个花钱买流量的投放页面来说，首屏慢 1 秒，跳出率就会急剧上升，直接影响转化。

**所以我的做法是，干脆放弃媒体查询，直接从组件级进行物理隔离，给 PC 和移动端各自设计一个完全独立的组件去实现。**

具体的技术落地是，我编写了一个 `detectDevice` 工具函数，在页面初始化时利用 `navigator.userAgent` 获取用户设备信息，并通过正则精确匹配来判断设备类型。然后在 Vue 的 `App.vue` 入口里，定义一个响应式的 `isMobile` 状态做 `v-if` / `v-else` 的条件渲染。
这样一来，如果是手机端访问，Vue 的虚拟 DOM 树根本就不会挂载 PC 端的组件。再配合打包工具的异步组件加载机制，做到了真正的**资源按需加载**，DOM 节点数和初始脚本体积大幅缩减，把首屏体验做到了极致，也**保障了多端展示与交互的一致性。**

在移动端的具体适配上，我使用了 **PostCSS-px-to-viewport** 方案将样式转换为 `vw` 来实现像素级还原。
**为什么选择 VW 方案呢？** 主要是为了性能。相比于传统 `rem` 方案需要依赖内联 JS 去动态计算视口并监听 `resize` 事件，`vw` 的转换是在 Vite 的构建打阶段就提前完成的，这极大减轻了客户端浏览器的渲染压力。同时，借助刚才提到的组件级拆分，我在 PostCSS 里配置了 `selectorBlackList` 黑名单，把 PC 端组件的类名全都过滤排除了，这样它就只会转换移动端的样式，避免了两端的响应式干扰。”

## 🌟 亮点二：打通“流量来源-用户行为-转化归因”全链路数据闭环

**👨‍💻 面试官提问：** “简历中提到你封装了 UTM 参数解析，还打通了全链路数据监测，能不能详细说一下这个过程？”

**🗣️ 您的回答（参考话术）：**

*(辅助理解的概念备忘)*
- **UTM 参数**（Urgency Tracking Module）是附加在 URL（网址）末尾的一段特定代码。它的作用是帮助网站所有者追踪流量来源。在代码里，我们使用原生 API `window.location.search` 获取 URL `?` 后的字符串，然后借由 `new URLSearchParams()` 将字符串转换为对象，方便提取。
- **PostHog** 是一个一站式分析平台，可以追踪页面浏览、点击、自定义事件。尤其是它的**录屏回放功能**，可以记录用户在网站上的鼠标移动、点击、滚动等真实操作过程；还有它的**可视化漏斗分析（Funnel）**功能，能看清用户在哪一步流失，还能统计访问量、停留时间和地区等信息。

**整个核心数据的串联流程是这样的：**
1. **首先是解析与身份绑定：** 当用户点击特定广告进入落地页时，URL 会自动携带 UTM 参数（如广告来源 Facebook 或 Instagram、广告组别等）。我在前端封装了一个解析模块，把提取的 UTM 字符串解析为对象并马上发给后端，换取一个系统内部生成的、唯一的 `Session ID`。
2. **其次是状态保持：** 考虑到用户操作时可能会刷新页面或中途跳去查邮件，我将这个 `Session ID` 持久化存储到了 `localStorage` 里，防止归因追踪断联。
3. **最后是转化携带与多端上报：** 当用户最终触发表单提交时，前端在发送请求时不仅会把业务表单数据传给后端，还会强制携带这个 `Session ID` 给后端，这就确保了转化数据来源的精确统合。

与此同时，在表单提交成功的那一刻，我还结合了前面的第三方埋点：同时调用了 PostHog 的 `capture` 和 `identify` API，将该用户的最终行为和属性意图发给数据分析看板去呈现漏斗效果。”

## 🌟 亮点三：搭建纯前端响应式 CVR 实时计算与 A/B 测试看板

**👨‍💻 面试官提问：** “关于运营决策看板，你提到集成了实时 CVR 计算、线索分层以及 A/B 测试分析，能具体讲讲这个看板是怎么辅助团队优化 ROI（投资回报率）的吗？”

**🗣️ 您的回答（参考话术）：**

“ROI 的全称是 Return on Investment，中文翻译为‘投资回报率’。

这个运营决策看板，实现的功能首先是展示落地页页面传回的数据，也就是 sessionid、用户填写的邮箱，反馈内容，和 UTM 参数。 运营同学可以在看板上自由组合筛选条件，比如按设备类型、广告来源、广告组别或者具体的时间段来拉取数据。筛选完之后前端通过 `computed` 实时计算当前的 CVR 转化率，同时通过 `computed` 和 `filter` 计算分层线索比如仅 UTM，仅填邮箱，仅填写反馈等数据的数量。

第二是支持基于 UTM 的 A/B 测试多维追踪。 通上方增加的多维筛选器，运营同学可以在这里进行控制变量法的比对。比如，控制投放渠道不变，单单对比‘Facebook AI 自动投放’和‘手动精准投放’这两种方式，到底哪种方法收集到的有效线索更多、ROI 效益更好。

通过这个看板，团队在跑各类 A/B 测试时终于有了**可量化的实时数据支撑**。他们能根据数据表现迅速去迭代更吸引人的广告内容，或是选择更高效的投放方式，最终大幅优化整体的投放 ROI。”

**(补充说明：面试官如果追问技术细节，或者你觉得气氛合适可以主动抛出这个技术亮点 👇)**

“**补充一点技术细节：** 在这块看板的开发中，关于多维度的漏斗筛选和 CVR 计算，在 MVP（最小可行性产品）阶段，我并没有让后端去写复杂的 SQL 聚合接口，而是把原始明细数据拉到前端，**纯粹利用 Vue 3 的 `computed` 响应式依赖收集机制在前端即时重算。** 因为项目早期数据量级在预期内（几万条以内），这套方案让运营同学体验到了‘发板即看、极速响应’的丝滑感，甚至当他们临时需要改变指标定义时，我只需要在前端改个 `filter` 逻辑，几分钟就能上线，大大节约了开发迭代成本。”
